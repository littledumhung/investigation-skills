# 調查流程與多輪搜尋

1. 先從使用者文字與附件整理「原始記憶／確定事實／推定／未知」。只問會實質區分候選的問題；有可搜尋線索先開始。
2. 用 query_expander.expand 或 CLI --plan-only 產出查詢與時間範圍。小型詞彙表不是完整翻譯；Agent 補自然的中英日文變體、精確詞組、舊技術詞、平台、可能的檔名與網域。每個假設記錄理由。
3. 先用宿主公開網頁搜尋找原名、開發者、舊 URL；再查 Wayback／Common Crawl。影片／軟體優先搜尋公開中繼資料、原始嵌入碼、縮圖檔名、發行紀錄和引用。新聞與論壇是發現線索的來源；回溯原始出處。
4. 對命中結果讀頁面並建立候選表：名稱、年份、作者、平台、玩法／功能、外觀、符合特徵、矛盾特徵、來源。不要將搜尋摘要當完整證據。
5. 下一輪只使用新證據：精確標題、別名、舊路徑、作者或檔名。使用 --seen-query 與 --clue 保留已查語句並更新查詢；從 report.json 的 query_plan 與 investigation_log 接續。CLI 不會自行完成多輪推理。
6. 回溯最早可驗證記錄；區分觀察時間與事件時間。對每個重要候選主動查反證，尤其年代、平台、開發者及網域換手。
7. 用 identity_resolver.resolve 處理已人工驗證的證據；保存 evidence_store 圖與 log。Agent 搜尋紀錄也需補入同一 log（query、provider、searched_at、result_count、clues、next_reason、status）。
8. 報告目前最合理候選及未排除項目，不宣稱已確認未讀過的內容。達到模式預算或兩輪無新證據即停止。

日期語句如「我 2012 年玩過」只約束作品最晚已存在，並不表示 2012 年發布。回顧文章可晚於遊戲很多年。使用查詢年份時先當提示，再由證據決定是否排除。

可選 log 存 JSON／SQLite。不要把帳號金鑰、私人附件內容或秘密貼進查詢。搜尋紀錄中的結果數是實際取得數，不是整個網際網路的總數。
